## 1. Что это за проект

**CityMate** — многоязычный мобильный AI-помощник по жизни в новом городе для туристов, релокантов и экспатов. Ощущение, которое должно давать приложение: «я в незнакомом городе не потерян, рядом есть местный друг».

Пользователь выбирает страну и город (старт — **Турция → Алания**) и попадает в локальное пространство, где собрана вся важная информация: места, услуги, документы, афиша, новости, маршруты — и AI, который отвечает на бытовые вопросы с учётом города.

Ранее проект назывался **AI Релокант**. Сейчас переименован в **CityMate** и пересобран практически с нуля.

Ключевая ценность — снять боль «я не знаю, где это найти и кому доверять». Поэтому **доверие** к данным — главный приоритет продукта.

## 2. Для кого

Туристы (короткий визит), релоканты и экспаты (долгий срок, документы и быт), местные жители (бытовые вопросы), местный бизнес (рекламная площадка).

## 3. Технологический стек

- **UI:** React 19, react-router-dom 7, lucide-react (иконки), react-i18next (интерфейсные переводы, §8)
- **Сборка:** Vite
- **Данные:** Supabase (PostgREST + RLS). Схема и все миграции — SQL-файлы в `supabase/`, запускаются вручную в SQL-редакторе Supabase (порядок и назначение описаны в шапке каждого файла).
- **Auth:** Supabase Auth — регистрация/вход по email, сброс пароля по ссылке. Просмотр приложения без входа; вход нужен для избранного и снятия лимита AI. Подробности жизненного цикла сессии — §9.
- **AI:** через **серверный прокси** на Vercel (см. §6). Провайдер — **Google Gemini**, модель `gemini-2.5-flash` (константа в `api/chat.js` и `api/translate.js`). Ключ живёт ТОЛЬКО на сервере (`GEMINI_API_KEY`).
- **Google Places:** серверный прокси `api/places-search.js` (Places API New — Text Search) для ускорения наполнения каталога из формы админки (§7). Ключ `GOOGLE_PLACES_API_KEY` — ТОЛЬКО на сервере, эндпоинт закрыт под админа (fail-closed).
- **Сбор данных:** ручной ввод владельцем через админку (§7) + заявки бизнеса; при наполнении каталога — Google Places как структурированный источник (§7); RSS-автомониторинг новостей (Этап 0, §7) — суточный Vercel Cron кладёт турецкие заголовки в очередь модерации; AI-парсинг официальных источников — на будущее (§14).
- **Хостинг:** Vercel (Git-connected, push в `master` → авто-деплой). Serverless-функции — в `api/` (включая `api/cron/*` — задачи из блока `crons` в `vercel.json`; защита — `CRON_SECRET`).
- **Аналитика:** Vercel Analytics (или Google Analytics) — счётчик посетителей/установок.
- **Тип:** PWA (манифест + иконки; `sw.js`). Иконки приложения собраны из логотипа (сине-бирюзовый глобус+пин): `public/logo.png` (значок в шапке), `favicon-64`, `apple-touch-icon`, `pwa-192x192`, `pwa-512x512`, `pwa-maskable-512x512` (maskable — с safe-зоной). Авто-обновление PWA обеспечивается заголовками `Cache-Control: no-cache` для `/`, `/index.html`, `/sw.js` в `vercel.json` (§9).

## 4. Архитектура и экраны

City-scoped, но с разными правилами скоупинга по типам контента — см. §5. После выбора города весь контент фильтруется по нему (места), либо по стране активного города с сортировкой по близости (афиша), либо по набору городов-галочек (новости/гайды).

**Принцип навигации (важно): AI → поиск → категории.** CityMate — это «спроси и реши», а не справочник. Люди не листают категории, они пишут «стоматолог», «пряжа», «торт». Поэтому на каждом экране сверху способ сразу спросить/найти: на главной — AI-строка «Спроси CityMate…»; в каталоге — текстовый поиск «Что ищете?» первым элементом (`searchPlaces`, ILIKE по имени/адресу), и только под ним категории. Поиск приоритетнее листания.

**Роуты (`src/App.jsx`):** `/welcome` (онбординг, вне таб-бара), `/reset-password` (вне онбординг-гарда и таб-бара), затем таб-шелл (`Layout`): `/` (Home), `/catalog`, `/catalog/:categorySlug`, `/catalog/place/:placeId`, `/events`, `/events/:eventId`, `/news`, `/news/:newsId`, `/guides`, `/guides/:guideId`, `/markets` (экран «Все рынки» по дням недели, `Markets.jsx`, п.8), `/sos` (экстренная помощь, `Sos.jsx`, п.9), `/weather` (детальный прогноз, п.1a), `/favorites`, `/chat`, `/profile`, `/admin` (сам редиректит не-админов). До онбординга любой роут уводит на `/welcome`. Пока активна ссылка сброса пароля (`recovering`) — рендерится ТОЛЬКО `ResetPassword`, что бы ни было в URL.

**0. Экран приветствия (`Welcome.jsx`).** При первом запуске: земной шар, анимация «Добро пожаловать» поочерёдно на всех языках приложения (стиль iOS «Hello»). Ниже — три селектора: страна / город / язык. Неактивные страны/города показываются, но помечены «(скоро)» и недоступны (список курируемый). Сам экран — на английском; после выбора языка всё остальное идёт на нём. Выбор сохраняется в localStorage (`AppProvider`); при следующих запусках сразу открывается главная. Сменить страну/город/язык можно позже (город — на главной, страна — в профиле).

1. **Главный экран города (`Home.jsx`)** — заголовок (логотип-значок `public/logo.png` + вордмарк «CityMate» + кнопка выбора города текущей страны + колокольчик; текстовая заглушка «CM» убрана), строка AI-поиска «Спроси CityMate…» с быстрыми вопросами, погода + температура воды (по координатам активного города), курс валют (базовая валюта по стране, §перечень ниже), новости сегодня, **рынки сегодня** (по недельному расписанию, §перечень ниже), афиша (региональный ряд `fetchRegionalEvents`). **Без** нижнего блока с фильтрами дат и рядом категорий — по решению владельца убран; категории живут в «Каталоге». Тап по погодной карточке ведёт на детальный экран погоды (п.1a).

   **1a. Экран погоды (`WeatherDetails.jsx`, роут `/weather`)** — детальный прогноз по активному городу: почасовой на сегодня (горизонтальный ряд), 10-дневный прогноз (полная дата, локализованная) и температура воды. Фото-шапка города (`CITY_HERO` — бесхозное фото не заимствуется: у кого есть своё фото — оно, у остальных универсальная небо-заглушка `public/welcome-sky.png`). Иконки погоды — цветные Meteocons (`src/lib/weatherIcons.js`), маппинг WMO-кода. Курс валют на главной — базовая валюта следует активной стране (`baseForCountry`: Турция → ₺ TRY, ОАЭ → AED; `src/lib/currency.js`).
2. **AI-помощник (`Chat.jsx`)** — сердце приложения. Свободный ввод, ответ с учётом города, заземлён на проверенную базу (§6).
3. **Каталог / Услуги (`Catalog.jsx`, `CatalogCategory.jsx`, `Place.jsx`)** — компании и специалисты. Скоуп строго по активному городу. Карточки с телефоном/WhatsApp/маршрутом/языками/графиком. Метки «проверено»/«продвигается». **Группировка по району:** подкатегория **`groceries`** (продуктовые магазины) выводится сгруппированной по `places.district` (районы A→Z, без района — в конце отдельным блоком `GROUPED_SUB_SLUG` в `CatalogCategory.jsx`); все остальные категории/подкатегории — плоский список. Каталожная категория **«Рынки» удалена** (дублировала экран рынков `/markets`, п.8).
4. **Документы и жизнь (`Guides.jsx`, `Guide.jsx`)** — инструкции (ВНЖ, numarataj, нотариус, страховка…) и чек-листы (`checklist` jsonb). Обязательны дисклеймеры (§11). Мультигород (§5).
5. **Афиша и события (`Events.jsx`, `Event.jsx`)** — региональная (§5): события всей страны активного города, сортировка по дате → близости места проведения. Фильтр по городу (по месту проведения) и по датам (пресеты + произвольный диапазон). Страница деталей события — соцсети, сбор гостей, цена, ссылка, фото, маршрут.
6. **Новости города (`News.jsx`, `NewsArticle.jsx`)** — короткие выжимки (что произошло, кого касается, что делать, источник). Мультигород (§5).
7. **Куда пойти** — пляжи, парки, рестораны, маршруты (в рамках каталога/категорий; отдельного экрана-ленты пока нет).
8. **Магазины и рынки** — продуктовые магазины живут в каталоге (`shops→groceries`, группировка по району, п.3). Ротационные городские рынки — недельное расписание `market_schedule` (§5.7): блок «Рынки сегодня» на главной + отдельный экран **«Все рынки» (`Markets.jsx`, `/markets`)** со всеми активными рынками, сгруппированными по дням недели. Каталожной категории «Рынки» больше нет (удалена, дублировала этот экран).

9. **SOS — экстренная помощь (`Sos.jsx`, `/sos`)** — статичный экран **БЕЗ AI** (в панике никто не ждёт ответа чата): только константы из `src/lib/sosConfig.js` / `sosPhrases.js` и три дешёвых запроса, экран рисуется мгновенно. Вход — **красная кнопка SOS в шапке главной**, рядом с колокольчиком (не среди чипов: ряд чипов скроллится вбок, ленты — вниз, и кнопка могла бы оказаться за экраном ровно тогда, когда нужна). Блоки сверху вниз по срочности:
   1. **Звонок в экстренные службы** — самая крупная кнопка `tel:`. Номер и подпись берутся из конфига **по стране**: Турция → `112` с честной подписью «единый номер: скорая/полиция/пожарные»; ОАЭ → `999` (полиция) + отдельные кнопки `998` (скорая) и `997` (пожарные), потому что единого номера там НЕТ и утверждать обратное нельзя (§11). Страна без проверенного номера — блок не рисуется.
   2. **«Отправить мою геолокацию близкому»** — `navigator.geolocation` → ссылка `https://maps.google.com/?q=<lat>,<lng>` → Web Share API, fallback — буфер обмена, затем показ ссылки текстом. **Ничего не хранится и не уходит на сервер**: координаты живут только в state компонента.
   3. **«Ближайшая больница»** — approved-места активного города из подкатегории `hospitals` (`fetchHospitals`), тап — обычная карточка места. С разрешённой геолокацией сортируются по реальному расстоянию (`haversineKm`, `src/lib/geo.js` — клиентский порт SQL-функции `haversine_km`), без неё — просто список. Геолокация **не запрашивается на маунте** — только по явному тапу.
   4. **«Дежурная аптека (nöbetçi eczane)»** — кнопка-ссылка на официальный список аптечной палаты, URL в `sosConfig.js` по slug города (Алания/Анталья и другие районы провинции → `antalyaeo.org.tr`). Автопарсинг НЕ делаем (§14) — непроверяемое «открыто сейчас» отправит человека через город в 3 ночи зря. Для города без URL блок скрыт.
   5. **«Моё консульство»** — по гражданству пользователя (§5.9). Три честных состояния: гражданство задано и запись есть → карточка его консульства (крупно `emergency_phone` с пометкой «24/7», ниже обычный телефон, часы, адрес с маршрутом через `directionsUrl`, сайт); гражданство задано, а записи нет → прямое «нет данных» + совет искать посольство в столице страны пребывания (Анкара / Абу-Даби); гражданство не задано → мягкий промпт с переходом в профиль **плюс** полный список консульств страны пребывания.
   6. **«Готовые фразы»** — статичный список `src/lib/sosPhrases.js`. Турецкий текст — **константа**, показывается всегда и крупно (экран показывают врачу/прохожему), тап раскрывает его на весь блок; ниже транслитерация без диакритики как подсказка произношения. Смысл фразы — через i18n-ключи `sos.phrases.*`.

   **Гражданство пользователя** — отдельная настройка профиля (`citizenship` в `AppProvider`, свой ключ localStorage `citymate.citizenship.v1`, НЕ внутри записи selection: та переписывается целиком при каждой смене страны/города, а гражданство должно её пережить). Список стран — `CITIZENSHIP_COUNTRIES` в `sosConfig.js` (только ISO-коды; названия локализует `Intl.DisplayNames`, поэтому 13 языков не требуют ручной поддержки). **Из языка интерфейса НЕ выводится** — русскоязычному гражданину Казахстана нужно казахское консульство.

**Нижнее меню — 5 вкладок (`TabBar.jsx`):** Главная / Каталог / Избранное / AI чат / Профиль.

**Дизайн (утверждён по макетам):** чистый «воздушный» стиль в духе iOS — светлый фон, скруглённые карточки, мягкие тени, крупный заголовок. Принцип: «за 10 секунд понятно, куда нажать».

## 5. Модель данных и скоупинг (Supabase)

Все таблицы и миграции — в `supabase/*.sql`. Базовая схема — `supabase/schema.sql`; каждая последующая фича добавлена отдельным идемпотентным файлом (шапка файла описывает порядок применения). RLS: анон/authenticated читают только `status = 'approved'` (у справочников — читается всё; у `market_schedule` — только `is_active`); все записи и модерация — через админскую RLS (`public.is_admin()`, таблица `admins`) или service_role.

### 5.1. Справочные таблицы (читаются целиком; неактивные показываются как «(скоро)»)

- **`countries`** — `code` (ISO alpha-2), `name`, `is_active`, `sort_order`.
  Реально заведены и **активны**: **Turkey (TR)** и **UAE (AE)**. Инактив-демо: Indonesia (ID), Thailand (TH).
- **`cities`** — `country_id`, `slug` (уникален в пределах страны), `name`, **`latitude`/`longitude`** (нужны для сортировки афиши по близости), `is_active`, `sort_order`.
  Активные города **Турции** (`cities-turkey-seed.sql` + сид схемы): Alanya (стартовый), Antalya, Kemer, Belek, Side, Mersin, Adana, Kaş, İzmir, Istanbul, Bodrum, Marmaris, Ankara — все с координатами.
  Активный город **ОАЭ** (`country-uae-seed.sql`): Dubai.
- **`categories`**, **`subcategories`** — дерево категорий (`slug`, `name`, `icon` = имя lucide-иконки, `is_active`, `sort_order`).

### 5.2. Контентные таблицы (модерация: `status` / `source` / `verified_at`)

- **`places`** — карточка каталога: имя, описание, адрес, координаты, телефон, whatsapp, `hours` (jsonb), `languages` (`lang_code[]`), `photos` (`text[]`), `maps_url` (готовая ссылка на маршрут, §5.8), `district` (район — используется для группировки `groceries` в каталоге, §4/п.3; не переводится), `is_verified` («проверено/партнёр», ставит владелец), `is_promoted` (платное размещение, честно помечается). **Рейтинг НЕ хранится и НЕ показывается** (§13).
- **`events`** — афиша. Помимо базовых полей (title, description, location, координаты, `starts_at`/`ends_at`, `url`, `image_url`) есть (см. §5.4 и `events-fields.sql`): соцсети `instagram`/`telegram`/`whatsapp`, сбор гостей `gathering_at`, ценообразование (`price_type`, `price_from`, `price_to`, `price_deposit`, `price_currency`), и **`venue_city_id`** (город проведения; см. скоупинг ниже).
- **`guides`** — «Документы и жизнь»: `title`, `body` (markdown), `checklist` (jsonb), `disclaimer`, `source_url`.
- **`news`** — короткие новости: `title`, `summary`, `body`, `source_name`, `source_url`, `image_url`, `published_at`.
- **`ads`** — рекламные/партнёрские карточки (всегда визуально помечаются, §11).

### 5.3. Правила скоупинга ПО ТИПАМ КОНТЕНТА (ключевое)

Скоуп различается намеренно — это продуктовое решение, а не техдолг.

- **КАТАЛОГ (`places`)** — **один город**. Скоуп строго по активному городу (`city_id`). В Дубае не показывается то, что в Алании. Читается через `publicContentQuery`/`fetchPlaces`/`searchPlaces` (`src/lib/content.js`).
- **НОВОСТИ и ГАЙДЫ** — **мультигород** (`news-guides-multi-city.sql`). Одна запись может показываться в НЕСКОЛЬКИХ городах одной страны без дублирования — через link-таблицы **`news_cities`** / **`guide_cities`** (галочки городов в админке). Реальные FK дают `ON DELETE CASCADE` в обе стороны (удаление записи → её линки исчезают; удаление города → его линки исчезают). Показ без дублирования: `fetchContent` делает `!inner`-join по city_id (пара уникальна). Старая колонка `city_id` оставлена только для отката (NOT NULL снят), админкой больше не пишется.
- **СОБЫТИЯ (афиша)** — **два разных понятия города** (`events-multi-city.sql` + `events-venue-city.sql`):
  * **`venue_city_id`** — ОДИН город, где событие физически проходит. По нему меряется близость для сортировки.
  * **`event_cities`** (галочки «где показывать») — НАБОР городов, в чьей афише событие видно. Курируется вручную в админке; venue-город НЕ добавляется в этот набор автоматически.
  * **Видимость** события в афише города X ⇔ X есть среди галочек `event_cities`. Если venue-город не отмечен — событие там не появляется (никакого неявного авто-добавления).

### 5.4. Граница СТРАН — жёсткая везде

- Для новостей/гайдов/событий каждая link-таблица имеет **before-триггер `enforce_*_same_country`**: нельзя привязать город из страны, отличной от страны уже привязанных городов. Запись не может охватывать две страны, что бы ни прислал клиент. Дубай не видит турецкое событие, потому что id Дубая нет в его линках.
- Региональная афиша (`events_by_country_proximity`) возвращает событие, ТОЛЬКО если собственный активный город пользователя — среди галочек `event_cities`; а город принадлежит ровно одной стране → перекрёстной утечки нет. (Осознанно НЕ добавляют venue↔links межтабличный триггер — он бы дедлочил легитимную смену страны при редактировании; границей служит видимость, а не дистанция сортировки.)
- **ПРЯМЫЕ ССЫЛКИ на карточку (по id)** — `fetchPlace`, `fetchEvent`, `fetchNewsItem`, `fetchGuide` — открываются **ВСЕГДА**, без city-guard и без скрытия прошедших событий. Это **осознанное решение** (лояльность): расшаренная/сохранённая ссылка должна открыться у кого угодно, даже на следующий день. Фильтрация по городу/стране — только для лент/списков.

### 5.5. Региональная афиша по близости (RPC + haversine)

- **`haversine_km(lat1,lon1,lat2,lon2)`** — расстояние по большой окружности, `immutable`, NULL-safe (недостающая координата → NULL, сортируется в конец).
- **`events_by_country_proximity(p_city_id, p_from default null, p_to default null)`** — серверная функция, единственный источник региональной ленты. Считает всё server-side (дистанция, отсечка «не прошедшее», видимость/страна), чтобы порядок был одинаков у всех и телефоны не считали haversine по всей ленте. `security invoker` — RLS внутри действует (только approved).
  - **Видимость/страна:** join `event_cities` по `p_city_id` (ровно один линк на событие → без дублирования).
  - **«Не прошедшее»:** оставляем события, чьи `starts_at` ИЛИ `ends_at` ≥ начала сегодняшнего дня **по времени Турции** (Europe/Istanbul, UTC+3) — чтобы лента не «переключалась» на несколько часов раньше/позже у пользователей в других поясах; плюс события без даты.
  - **Порядок (ORDER BY):** `starts_at` (ASC, nulls last) → близость venue к `p_city_id` (`haversine_km`, ASC, nulls last) → `e.id` (стабильный tie-break). То есть хронологически по дате начала; близость venue — вторичный ключ (свой город = 0, разрывает ничью при равном `starts_at`; событие без venue/координат уходит в конец). ⚠️ Это фактическое поведение кода: близость — вторичный ключ ПОСЛЕ `starts_at`, а не «внутри календарного дня до времени».
  - **Фильтр дат:** необязательные `p_from`/`p_to` (абсолютные инстанты, вычисляет клиент в турецком времени — `computeDateRange`). При активном фильтре событие без даты скрывается; overlap-правило совпадает с клиентским `fetchUpcomingEvents`. Оба NULL ⇒ фильтра нет (существующие вызовы — Home-ряд, «Все даты» — работают без изменений).
- Клиентские читатели (`src/lib/content.js`):
  * **`fetchRegionalEvents(cityId, {limit, range})`** — региональная лента (Home-ряд + Events «Все города»): RPC выше.
  * **`fetchUpcomingEvents(cityId, {range})`** — одногородний вид (когда пользователь сузил ленту до города): фильтр по **`venue_city_id`** (что происходит В этом городе), а не по галочкам показа.

### 5.6. Служебное в схеме

- **`content_translations`** — одна полиморфная таблица переводов для всех типов (`entity_type`/`entity_id`/`lang`/`field`/`value`), 13 языков. FK нет → при физическом удалении родителя переводы чистятся вручную кодом (см. §7). `content_is_approved()` гейтит публичное чтение переводов (approved-родитель; для `market_schedule` — `is_active`).
- **`market_schedule`** — недельное расписание рынков (§5.7).
- **`admins`** — реестр админов (гейт всей записи/модерации, `public.is_admin()`).
- **`ai_usage`** — посуточный учёт лимита AI-чата (§6).
- Триггер `set_updated_at` на всех редактируемых таблицах; `enforce_*_same_country` на link-таблицах; `purge_past_events` — авто-очистка прошедших событий (§5.4/§7).
- Enum-ы: `content_status` (pending/approved/rejected), `content_source` (manual/ai_parse/business_submission), `lang_code` (13 языков).

### 5.7. Рынки — недельное расписание (`market_schedule.sql`, `market-schedule-multi.sql`)

- Рынки в Алании ротируются по неделе (свой район каждый будний день). Вместо ежедневного создания/удаления «места-рынка» расписание задаётся ОДИН раз. Это **справочные данные владельца** (флаг `is_active`, а НЕ очередь модерации `status`).
- Поля: `city_id`, `day_of_week` (**ISO-8601: 1=Пн … 7=Вс**, неделя с понедельника), `name` (район/рынок, переводится), `image_url`, `hours` (текст, не переводится), `address` (не переводится), `latitude`/`longitude` (для маршрута), `is_active`.
- **Несколько рынков в один день недели** разрешены (уникальный `(city_id, day_of_week)` намеренно снят в `market-schedule-multi.sql` — в Алании до трёх рынков в день).
- Блок «Рынки сегодня» на главной (`fetchTodayMarkets`) показывает ВСЕ активные строки текущего дня недели **по времени Турции** (`turkeyDayOfWeek()`), имя района локализуется. Пустой день (напр. воскресенье) → аккуратная заглушка «сегодня рынка нет».
- **Экран «Все рынки» (`Markets.jsx`, `/markets`)** — все активные рынки города, сгруппированные по дням недели (`fetchMarketSchedule`-подобное чтение всей недели). Именa районов локализуются; часы/адрес — как есть.
- ⚠️ Рельса рынков и экран `/markets` живут по расписанию `market_schedule`, а НЕ по каталожной категории. Прежняя каталожная категория «Рынки» **удалена** (дублировала этот экран).

### 5.8. Маршруты (`src/lib/maps.js`)

`directionsUrl(target)` — единый источник ссылки «нажать адрес → открыть в Google Maps». **Приоритет (важно):** (1) если у записи есть `maps_url` (готовая ссылка, которую владелец вставил через «Поделиться → Копировать ссылку») — открывается СТРОГО она, как есть, без пересборки (в т.ч. короткие `maps.app.goo.gl`); (2) иначе точные координаты → `maps/search/?api=1&query=<lat>,<lng>`; (3) иначе текстовый адрес (последний резерв — в Турции адрес часто целый район, поэтому он в самом конце). `null`, если ничего нет. Колонка `maps_url` (nullable text, `supabase/maps-url.sql`) есть у `places`/`events`/`market_schedule`; не переводится (§8), координаты сохранены как резерв. Используется одинаково в рельсе рынков, карточке места и событиях. Открывается в новой вкладке.

### 5.9. Консульства (`consulates.sql`)

- Справочник владельца для блока «Моё консульство» на экране SOS (§4/п.9). Как `market_schedule` — флаг `is_active`, а НЕ очередь модерации; плюс `verified_at` (когда владелец последний раз сверял номера с официальным сайтом).
- **Сидов НЕТ и быть не должно.** Каждая запись вносится владельцем вручную с официального сайта представительства. Выдуманный или «примерный» экстренный номер здесь наносит реальный вред — это жёстче общего правила §11.
- **Две РАЗНЫЕ страны в одной строке** (главное, что легко перепутать):
  * **`citizenship_country_code`** — чьих граждан обслуживает (напр. `RU`). Обычный ISO alpha-2 и намеренно **НЕ FK на `countries`**: `countries` — это страны, которые покрывает приложение, а гражданство может быть любым. Матчится по коду с настройкой профиля.
  * **`host_country_id`** — FK на `countries`, страна, где представительство действует. Держит жёсткую границу стран (§5.4): пользователь в Турции видит только представительства в Турции.
- Прочие поля: `name`, `city_label` («Анталья» — выводится как «консульство в Анталье»), `emergency_phone` (круглосуточная линия — главное поле таблицы), `phone`, `hours`, `address`, `maps_url`, `latitude`/`longitude`, `website`, `sort_order`.
- RLS: анон/authenticated читают только `is_active`; вся запись — админская (`public.is_admin()`).
- **В `content_translations` НЕ заводится** (§8): все поля — имя собственное, телефон, адрес или URL, а такое нигде не переводится. Подписи блока — обычные i18n-ключи `sos.*`.

## 6. AI-помощник (`api/chat.js`)

- Вызов модели ТОЛЬКО через серверный прокси `POST /api/chat` (Vercel serverless). Ключ — из `process.env.GEMINI_API_KEY`, **никогда** не из клиентского бандла. Модель — `gemini-2.5-flash`.
- **Персона по городу:** активный город/страна для персоны и заземления берутся из `city_id` запроса (не хардкод «Алания») — прокси резолвит город/страну через Supabase.
- **Заземление (grounding) — расширено с одних мест на 5 типов данных.** Перед вызовом Gemini прокси читает approved-места активного города (`fetchApprovedPlaces`, до `MAX_PLACES = 30`, promoted+verified в приоритете) **плюс** события, новости, гайды и рынки — через ТЕ ЖЕ функции видимости, что и экраны, поэтому AI видит РОВНО то же, что пользователь на экранах своего города, и граница города/страны держится:
  * события → RPC `events_by_country_proximity` (видимость `event_cities` + граница страны живут внутри неё), не сырой `select * on events`;
  * новости → `news_cities` !inner join по city_id (+ approved);
  * гайды → `guide_cities` !inner join по city_id (+ approved);
  * рынки → `market_schedule` на сегодняшний день недели по времени Турции, только `is_active`.
  Модель обязана отвечать строго из этих списков (без выдуманных мест/событий/дат/цен/новостей/рынков); если раздел пуст — честно сказать «(none)».
- **Сужение и детали:** AI сужает выдачу под вопрос пользователя и даёт детали (время/цена/адрес/описание/соцсети). В ответ включаются **кликабельные ссылки на карточки** объектов (`/events/<id>`, `/news/<id>`, `/guides/<id>`, места) с защитой от выдуманных ссылок: whitelist разрешённых путей + требование корректного UUID/«Card link:»; нельзя линковать объект без ссылки (рынки ссылки не имеют).
- AI-ответы генерируются на языке пользователя на лету (`lang` в теле запроса).
- **История чата** сохраняется локально (`src/lib/chatHistory.js`: `loadChatHistory`/`saveChatHistory`/`clearChatHistory`, localStorage, потолок числа сообщений; кнопка «Очистить чат»). Восстановление истории при открытии экрана НЕ тратит дневной лимит (лимит списывается только на реальный вызов Gemini).
- **Лимит бесплатного тарифа:** `DAILY_LIMIT = 10` сообщений в день на пользователя, считается **server-side в таблице `ai_usage`** (по UTC-дню). Сверх лимита Gemini не вызывается — мягкий отказ. Платная разблокировка — на будущее.
- `vercel.json`: SPA-rewrite не перехватывает `/api` (`source: /((?!api/).*)`).

## 7. Контент-пайплайн и админка (AI/владелец → человек утверждает)

Админ-экран (`src/pages/Admin.jsx`, редиректит не-админов; гейт — таблица `admins` + RLS) — рабочий центр наполнения и модерации. Хелперы данных — `src/lib/admin.js`.

**Что умеет админка:**

1. **Выбор страны/города во всех формах** (`fetchAllCities`, включая неактивные «(скоро)» — контент можно готовить до запуска города). `city_id` каждого места ставится из активного города.
2. **Скоуп по типам:**
   - Места — один город.
   - Новости/гайды/события — **галочки городов** (link-таблицы; `setContentCities` диффит и меняет минимально, удаляя перед вставкой, чтобы смена страны не смешала две страны — жёсткую гарантию даёт триггер).
   - События — дополнительно **город проведения** (`venue_city_id`) отдельным селектором.
3. **Модерация:** запись создаётся `status = pending`; владелец approve/правит/reject; в приложение отдаётся только `approved`.
4. **Кнопка удаления** записей — физическое удаление строки (`deletePlace`/`deleteContent`/`deleteMarketScheduleDay`) с **очисткой переводов** (`content_translations` полиморфна, без FK-каскада — чистится вручную). Необратимо, требует подтверждения.
5. **«Сохранить и перевести»** и **панель переводов:** автоперевод через `POST /api/translate` (Gemini, закрыт для админов) переводит текстовые поля записи с исходного языка на **остальные 12** из 13 и кладёт в `content_translations`. Переводимые поля — `TRANSLATABLE_FIELDS` (напр. places: name/description; news: title/summary/body; events: title/description; guides: title/body; market_schedule: name). Телефоны/адреса/URL/часы/координаты НЕ переводятся.
6. **Рынки** — редактор недельного расписания (`fetchMarketSchedule`/`saveMarketScheduleRow`/`deleteMarketScheduleDay`).
   **Консульства** — такой же редактор-справочник для экрана SOS (`fetchAdminConsulates`/`saveConsulate`/`deleteConsulate`, §5.9): вкладка скоупится по стране пребывания, у каждой записи свой `is_active`, удаление с подтверждением, поле «Проверено» под дату сверки с официальным сайтом. Панели переводов нет намеренно (§5.9). **Никаких сидов и импорта — только ручной ввод с официального сайта представительства.**
7. **Авто-очистка прошедших событий** — «ленивая»: при открытии вкладки событий вызывается `purgePastEvents` (буфер `bufferDays = 7`); опционально серверный `pg_cron` (`events-cleanup.sql`).
8. **Загрузка фото** — бакет `place-photos` (публичное чтение, запись только админам), переиспользуется новостями/событиями.
9. **«Найти в Google»** в форме места (`searchGooglePlaces` → `applyGooglePlace`, `src/lib/admin.js` + прокси `api/places-search.js`, §7.1) — владелец вводит запрос, выбирает результат, и **текстовые** поля автозаполняются: название, адрес, координаты, часы, телефон, сайт, `maps_url`. Фото/логотип/район/описание/категория/метки — владелец ставит вручную (автозаполнение никогда не затирает поле пустым значением). Опциональный ускоритель наполнения (особенно сети — A101, BIM, Migros), не обязателен.

**Сбор данных (пайплайн):** сейчас — ручной ввод владельцем (bootstrap каталога — Google Places через прокси `api/places-search.js` как структурированный источник, §7.1; после запуска бизнес попадает через платную заявку, §12). Новости — RSS-автомониторинг (§7.2, Этап 0) кладёт турецкие заголовки в очередь модерации; парсинг остальных официальных источников (иммиграция, госновости) — на будущее (§14). Черновик → `pending` → модерация → `approved` (публикация).

### 7.1. Google Places в форме места (`api/places-search.js`)

- Серверный прокси к **Places API (New) — Text Search** (`places:searchText`). Ключ `GOOGLE_PLACES_API_KEY` — ТОЛЬКО на сервере, в клиентский бандл не попадает; Google вызывается только отсюда.
- **Закрыт под админа (fail-closed)**, как `api/translate.js`: сверяет Supabase-токен вызывающего (`/auth/v1/user`) и его наличие в `admins` через service_role. При любой ошибке — отказ (чтобы платную квоту Places нельзя было слить просто залогинившись).
- **FieldMask** запрашивает ровно потребляемые поля (id, displayName, formattedAddress, location, regularOpeningHours, internationalPhoneNumber, websiteUri, googleMapsUri) — Google не биллит лишнего. `languageCode` из белого списка 13 языков (§8), иначе `en`. Лимит `MAX_RESULTS = 8`. Пустой результат — мягкий исход, не ошибка.
- Возвращает компактную форму `{ id, name, address, lat, lng, hours, phone, website, mapsUrl }`. Фото НЕ тянутся.

### 7.2. RSS-автомониторинг новостей — Этап 0+1 (`api/cron/ingest-news.js`)

- **Vercel Cron раз в сутки** (`vercel.json` → `crons`, `schedule: "0 6 * * *"` UTC). Защита — `Authorization: Bearer <CRON_SECRET>` (Vercel Cron шлёт его сам); без токена — 401.
- **Что делает:** обходит курируемый список турецких RSS-лент через `rss-parser` (сейчас 2: `rss.haberler.com/rss.asp?kategori=antalya` — «Haberler — Antalya», и `gazetealanya.com/rss` — «Gazete Alanya»; старые haberantalya-ленты ушли за Cloudflare-челлендж и отброшены). Ленты по провинции Анталья/Аланье покрывают Аланью → все мапятся на Аланью. **Fail-soft:** сломанная лента пропускается (`feedErrors`), не роняет прогон.
- **Дедуп** — один батч-select по `news.source_url` на весь прогон (не по элементу). **Лимит `MAX_NEW_PER_RUN = 15`** (поднят с 5) новых строк за прогон (остальное подхватится назавтра — очередь модерации остаётся посильной).
- **Справедливое round-robin деление лимита между лентами:** слоты делятся поровну между активными лентами (при 2 лентах и лимите 15 → до 8 + 7), недобранные слоты одной ленты уходят другой (итог всё равно ≤ `MAX_NEW_PER_RUN`, ничего не теряется). Чтобы лента целевого города (Gazete Alanya) не проигрывала более объёмной провинциальной (Haberler — вся Анталья) и обе гарантированно попадали в очередь. Пер-лентовую посадку видно в `insertedByFeed`.
- **Этап 1 — дословный перевод TR→RU через Gemini прямо в cron** (не при одобрении). Переводятся `title`/`summary` **дословно** (0 выжимки/пересказа/выдумки, §11; имена собственные/бренды/адреса не трогаются, §8) на **русский** — новости попадают в очередь модерации СРАЗУ по-русски. Турецкий оригинал не сохраняется (в `title`/`summary` лежит русский текст). Переводятся только ≤`MAX_NEW_PER_RUN` реально вставляемых строк — не весь пул кандидатов, чтобы дедуп-отсев не жёг квоту Gemini.
- **Перевод — fail-soft на каждый элемент:** если Gemini не ответил/протаймаутил, ключа нет, ИЛИ модель отказала по своему фильтру (`PROHIBITED_CONTENT` — бывает на криминале/насилии), новость **всё равно вставляется с турецким текстом**, прогон не падает; такие случаи считаются в `translateErrors`. Осознанный выбор: новость важнее перевода — владелец добьёт перевод или отклонит при модерации. Побочный полезный эффект: непереведённые (турецкие) строки в очереди — как правило криминал, удобный сигнал к отклонению.
- **Ядро перевода вынесено в общий модуль `api/_lib/translate-core.js`** (экспорт `translateFields`, тот же Gemini-промпт с защитой имён собственных; **никогда не бросает** — возвращает `{ ok: true/false }`); переиспользуется и в `api/translate.js` (админка/i18n-sync), и в cron. Префикс `_lib` держит файл вне роутинга Vercel.
- **Пишет в `news`** через service_role: `status = 'pending'`, `source = 'ai_parse'`; `source_url` обязателен (без ссылки элемент пропускается, §11); `city_id` оставлен NULL — видимость идёт через линк **`news_cities` на Аланью** (§5.3). Перевод на остальные 11 языков — позже, кнопкой «Сохранить и перевести» при одобрении (§7).
- **Поля `summary` (лог + JSON-ответ):** `candidates`, `uniqueLinks`, `inserted`, `insertedByFeed` (`{source_name: N}`), `skipped`, `translated`, `translateErrors`, `noLink` (+ пер-лентовый `noLink` в `feeds[]`), `feedErrors`, `insertErrors`, `cityResolved`.
- **Формат карточки новости — «анонс»:** заголовок + краткое RSS-`summary` + кликабельная ссылка на первоисточник. Полного текста статьи НЕТ (RSS отдаёт только заголовок и завлекалку), поэтому суть иногда неполна — full-text выжимка вынесена в будущее (§14).
- **Время прогона:** ~1 минута при 15 новостях (переводы последовательны); потолок функции 5 минут — запас большой.
- **Дальнейшие этапы — в §14/§13 (TBD):** Этап 2 — бейдж «RSS-авто» + ссылка на источник в админке; Этап 3 — таблица `news_sources` для управления лентами без деплоя; full-text выжимка сути статьи; распараллеливание переводов. Афиша (`etkinlik.io`), Telegram, госновости через «разбор по ссылке» — на будущее.

- **Служебный скрипт `npm run i18n:sync`** (`scripts/i18n-sync.mjs`, запуск ВРУЧНУЮ, НЕ в билде) — добивает **только недостающие** ключи локалей через Gemini (`/api/translate`, та же модель). Существующие переводы не трогает (byte-for-byte), плейсхолдеры/токены (`{{count}}`, `<1>`, `\n`, `₺ € $ %`) защищены и проверяются. `admin.*` (внутренний UI владельца) по умолчанию ПРОПУСКАЕТСЯ; `npm run i18n:sync -- --include-admin` переводит и их. Если ничего не пропущено — no-op, ключ Gemini не нужен.
- **Контент** — переводы на каждый язык в `content_translations` (§5.6); базовая строка хранит исходный язык, таблица — остальные. Заполняются автопереводом Gemini или вручную через админку (§7). Публичное чтение — `withTranslations()` (только approved-родитель, RLS).
- **AI-ответы** — на языке пользователя на лету (§6).

**Языки старта (ВСЕ сразу, 13):** русский (ru), английский (en), турецкий (tr), немецкий (de), украинский (uk), польский (pl), нидерландский (nl), чешский (cs), французский (fr), финский (fi), шведский (sv), норвежский (no), датский (da).

**⚠️ Спец-правило для имён собственных (артисты/бренды):** в события имена артистов и брендов вносятся **латиницей вручную** (напр. `Meladze`, а не `Меладзе`), а описания пишутся по-русски. Автоперевод намеренно НЕ трогает имена собственные — промпт `api/translate.js` явно запрещает переводить бренды/имена/адреса и просит вернуть их как есть.

## 9. Безопасность, сессии и служебное

- **Ключи и секреты — ТОЛЬКО на сервере** (переменные без префикса `VITE_`). Server-only: `GEMINI_API_KEY`, `GOOGLE_PLACES_API_KEY`, `CRON_SECRET`, Supabase `SUPABASE_SERVICE_ROLE_KEY`. `.env` — в `.gitignore`, в репо только `.env.example`.
- **Исключение — публичные ключи Supabase:** `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` предназначены для клиента (защищены RLS). Прокси переиспользует их для server-side публичных чтений под RLS.
- Прямые вызовы внешних AI/платных API из браузера запрещены — только через серверный прокси. `api/translate.js` и `api/places-search.js` дополнительно закрыты: сверяют токен вызывающего и его наличие в `admins` через service_role (fail-closed). Cron `api/cron/ingest-news.js` закрыт `CRON_SECRET` (Bearer), пишет через service_role.
- **Авто-обновление PWA:** `Cache-Control: no-cache` для `/`, `/index.html`, `/sw.js` в `vercel.json` — свежий деплой подхватывается без застревания в кэше.
- **Аутентификация (`src/context/AuthProvider.jsx`, `ResetPassword.jsx`, `SessionToast.jsx`, `authErrors.js`):**
  * **Сброс пароля** — ссылка из письма (implicit flow, `type=recovery` в хэше) распознаётся синхронно на boot; событие `PASSWORD_RECOVERY` поднимает лок `recovering` и форсит `/reset-password`, чтобы recovery-сессия НЕ была принята за обычный вход. Работает даже если ссылка открывает корень сайта.
  * **Lifecycle-refresh сессии для iOS:** тихий `refreshSession()` на boot (сбрасывает 7-дневный ITP-таймер script-writable storage) и при возврате вкладки в фокус (`visibilitychange`, троттлинг 3 мин) — чтобы «замороженная» вкладка не возвращалась с протухшим токеном и ложным «session expired». Ошибки refresh глотаются (не демотят пользователя).
  * **Человеческие ошибки** — `authErrors.js` маппит коды Supabase в понятные сообщения; `SessionToast` неинтрузивно уведомляет о реально пропавшей сессии (в отличие от явного «Выйти»).
- Коммиты — осмысленными порциями с понятными сообщениями. **Линтер:** ESLint (стандартный конфиг).

## 11. Доменные заметки (важно для доверия)

- **Юридические/документальные темы** (ВНЖ, numarataj, налоги): всегда дисклеймер «информация справочная, перед действием проверяйте у официальных источников/специалистов» (`guides.disclaimer`). Источник и дата проверки обязательны.
- **Новости:** проверяемый источник (`source_name`/`source_url`), короткий формат. Не публиковать непроверенное.
- **Экран SOS (§4/п.9) — правило «не выдумывать» действует вдвойне.** Экстренные номера, ссылка на дежурные аптеки и телефоны консульств либо **проверены**, либо блок **не рисуется вообще**. Никаких placeholder-номеров, никаких «наверное, как в Турции» по умолчанию для другой страны, никакого «единого номера» там, где его нет (ОАЭ). Источник каждой константы указан комментарием в `src/lib/sosConfig.js`; у консульств дата сверки — в `verified_at`. Неверный номер в экстренной ситуации хуже отсутствия номера.
- **Приватность геолокации:** координаты пользователя на экране SOS не сохраняются и не отправляются на сервер — запрашиваются только по явному тапу, живут в state компонента, используются для ссылки, которой пользователь делится сам, и для клиентской сортировки больниц.
- **Монетизация vs доверие:** платное размещение (`is_promoted`) и партнёрские карточки (`ads`) визуально и логически отделены от органических рекомендаций. Оплата не двигает AI-рекомендации. Метка «проверено» (`is_verified`) даётся владельцем за качество, а НЕ за оплату.

## 12. Монетизация (контекст продукта, не код)

**Для пользователей — бесплатно.** AI-чат — лимит ~10 сообщений/день на пользователя (§6); платная разблокировка — на будущее.

**Доход с бизнеса — три уровня:** (1) база каталога — наполняет владелец бесплатно; (2) вход в каталог по инициативе бизнеса — минимальная плата; (3) выделение (первым в категории, метка «рекомендуем», расширенная карточка, баннер) — дороже, желательно подписка. Также акции/баннеры, партнёрские комиссии.

**Принцип доверия:** базу полезных мест владелец держит сам и бесплатно (иначе при поиске «больница»/«ремонт кондиционера» пользователь ничего не найдёт). Платный верх честно помечается. Модель каталога — решено: все бизнесы в каталоге бесплатно, платят за выделение.

⚠️ **Цена — TBD.** Ориентир входа ~1000 TRY; выделение дороже; привязка к категории. На старте — первым бизнесам бесплатно/дёшево ради наполнения. Точная цена тестируется, сверяется с локальным рынком.
